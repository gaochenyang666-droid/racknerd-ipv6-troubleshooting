# VPS 代理故障分层排查清单

适用场景：服务器显示服务正常，但本地设备的代理经常超时。下面的命令仅作**最小化诊断参考**，其中的地址、端口需替换为自己的测试环境。请勿在公开 Issue 中粘贴完整配置和认证凭据。

## 0. 明确症状与对照

记录：时间、时区、客户端网络（Wi-Fi / 蜂窝）、IPv4 或 IPv6、端口、连续测试次数、超时值和错误文本。选一个同一分钟内已知正常的海外 HTTPS 网站作为对照，避免误把本地网络整体异常归因于某一台 VPS。

## 1. 检查服务端本机是否正常

在 Ubuntu VPS 上：

```bash
sudo systemctl status hysteria-server --no-pager
sudo ss -lunp | grep ':39000'
ip -br address
ip -6 route
```

这里假定服务名为 `hysteria-server`、UDP 端口为 `39000`。命令无输出不自动代表服务异常，需要核对自己的实际服务名和端口。若有防火墙，还要检查其 IPv6 UDP 放行策略。

检查关键日志（公开时脱敏）：

```bash
sudo journalctl -u hysteria-server -n 30 --no-pager
```

服务处于 active、端口在监听，只能说明进程基本正常，不能代替客户端验收。

## 2. 从客户端对比 IPv4、IPv6

在 macOS 上（先将示例替换成自己的真实地址）：

```bash
# IPv4 路径的 TCP 测试
nc -4 -vz -G 5 <VPS_IPV4> 22

# IPv6 路径的 TCP 测试
nc -6 -vz -G 5 <VPS_IPV6> 22

# IPv6 ICMP 探测，仅作连通性参考
ping6 -c 4 <VPS_IPV6>
```

注意：Hysteria 2 使用 UDP，22 端口 TCP 的成功不能直接证明 UDP/QUIC 可用。若当前 Mac 有 TUN 或 Fake-IP，需额外确认测试是否真正走预期的物理接口和路由；单独绑定一个源地址未必能绕过 TUN 劫持。

## 3. 双端抓包定位 TCP 报文

在有权限的环境中，从服务器和客户端分别抓取同一轮测试的报文，检查：SYN 是否到达、SYN-ACK 是否发出、客户端是否收到。Linux 端示例：

```bash
sudo tcpdump -ni any 'tcp port 22 or udp port 39000'
```

`tcpdump` 输出可能包含真实 IP 和端口，发布前需脱敏。服务器看见发包，仍不能确定是在互联网哪一跳丢失。

## 4. 正确测试 UDP

分清以下三件事：

1. 未监听 UDP 端口返回 ICMP Port Unreachable：只能说明部分往返路径可达。
2. UDP Echo 收到与原样相符的**应用载荷**：证明该轮真实 UDP 往返可用。
3. QUIC 完成 TLS 握手、代理实际转发 HTTPS：才算完整业务功能可用。

如果 UDP Echo 成功率很低，就先排除防火墙、网卡路由以及双端抓包所示的报文损失，再考虑协议参数。

## 5. 最终真实业务验收

如本地客户端已经启动 SOCKS5 入站监听（以下仅示例端口 `1080`），从客户端实际经过代理发请求：

```bash
curl --socks5-hostname 127.0.0.1:1080 \
  --max-time 15 -sS -o /dev/null -w '%{http_code}\n' \
  https://www.google.com/generate_204
```

再用可信的 IP 回显服务核对代理出口地址，连续请求至少 20 次，并进行十分钟稳定性测试及实际上传下载。每次都应确认请求确实经过目标代理，而没有被系统分流策略直连。

## 6. 不建议做的事情

- 不验证路径就频繁重装代理服务。
- 仅凭 `systemctl active`、Ping、端口监听判定代理成功。
- 仅凭 ICMP 错误回复断言 UDP 隧道稳定。
- 为修复代理随意清空防火墙或关闭 SSH 管理入口。
- 在公开日志、截图或提交记录中泄露密码、私钥、订阅地址。
