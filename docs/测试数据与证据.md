### 为什么不能把“UDP 10/10”当成隧道可用？

向关闭的 UDP 端口发送报文时，服务器可用 **ICMP Destination Unreachable / Port Unreachable** 回答。客户端套接字可能因此报告 `Connection refused`。这能支持报文的去程和 ICMP 回程可达，但没有验证服务端应用返回真实 UDP 载荷，更没有验证 QUIC 的多轮握手与持续吞吐。

## 三、IPv6 最终验收

| 项目 | 测得结果 |
| --- | ---: |
| IPv6 TCP 建连 | 20/20 |
| IPv6 SSH 握手 | 10/10 |
| 通过 Hysteria2 代理的真实 HTTPS 请求 | 20/20 |
| 真实 HTTPS 平均耗时 | 约 0.97 秒 |
| Google `generate_204` | 返回 HTTP 204 |
| YouTube、Telegram | 可达 |
| 代理出口 IP | 核对正确 |
| 下载 | 约 5.8 Mbps |
| 上传 | 约 11 Mbps |
| 连续 10 分钟测试 | 68 次请求，零失败 |
| iPhone 手机端后续验收 | 用户确认成功，具体成功率与网络类型未记录 |

同一台服务器和同一套 Hysteria2 服务，此轮对照的核心变量是**服务器入口从 IPv4 改为 IPv6**。这有力说明原来失败的瓶颈与 IPv4 路径相关，但不能断言发生了人为封锁，也不能直接定位丢包网元。

## 四、证据边界与快速复现

- 18:48 的 10/10 与 19:23、19:28、19:29 的真实 UDP Echo 测的是不同类型的往返通信，不能直接拼接、比较成同一个时间序列的应用层可用率。
- TCP 22 的 1/10 和 1/3 均为真实记录，但分别属于同分钟配对测试和随后的小样本探测。
- 最终验收验证了 Mac 的 IPv6 路径；手机端成功来自用户后续自测确认，详细成功率和网络类型并未记录。
- 可参考 [macOS 物理网卡对照脚本](../scripts/mac_path_probe.py) 对故障 IP 和对照 IP 进行低频轮换 TCP / TLS 握手检测。

## 五、未验证事项

- 上传、下载的长周期波动及峰谷时段差异。
- Mac 关机状态下的证书自动续期。
- 不同客户端网络对 RackNerd IPv6 的稳定性。
