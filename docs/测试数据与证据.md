### 为什么不能把“UDP 10/10”当成隧道可用？

向关闭的 UDP 端口发送报文时，服务器可用 **ICMP Destination Unreachable / Port Unreachable** 回答。客户端套接字可能因此报告 `Connection refused`。这能支持报文的去程和 ICMP 回程可达，但没有验证服务端应用返回真实 UDP 载荷，更没有验证 QUIC 的多轮握手与持续吞吐。

## 三、10 月 17 日同分钟 IPv4 / IPv6 TCP 对照

| 测试（同一分钟，各 10 次） | 成功 | 平均 TCP 建连耗时 |
| --- | --- | ---: |
| IPv4 TCP 22 | 8/10 | **2476 ms** |
| IPv6 TCP 22 | 10/10 | **323 ms** |

**关键点：成功率只是指标之一。** 即便 IPv4 有 8/10 次连通，平均 TCP 建连耗时仍约 2.5 秒，远慢于 IPv6。对于 TCP 承载的服务，后续 TLS 和应用层交互会进一步消耗时间预算。**Hysteria2 使用 UDP/QUIC，不能把 TCP 22 延迟直接等同于其 UDP/QUIC 握手耗时或失败原因。**

这项测试降低了原先跨时段比较的偏差；两种协议族的路由路径和网络处理方式本来就可能不同，因此只用来衡量当时两条**实际可用路径的差异**。原先 10 月 16 日约 19:2x 的 IPv4 测试与约 21:0x 的 IPv6 业务验收之间相隔约 1.5 小时，**不构成同分钟严格控制实验**。

## 四、IPv6 最终验收

| 项目 | 测得结果 |
| --- | ---: |
| IPv6 TCP 建连 | 20/20 |
| IPv6 SSH 握手 | 10/10 |
| 通过 Hysteria2 代理的真实 HTTPS 请求 | 20/20；同一目标 `api.github.com` 连续 20 次 |
| 真实 HTTPS 平均耗时 | 约 0.97 秒 |
| Google `generate_204` | 返回 HTTP 204 |
| YouTube、Telegram | 可达 |
| 代理出口 IP | 核对正确 |
| 下载 | 约 5.8 Mbps |
| 上传 | 约 11 Mbps |
| 连续 10 分钟测试 | 每约 15 秒一轮：Google `generate_204` + GitHub，34 轮共 68 次；0 失败 |
| 该轮请求最大耗时 | 6.65 秒 |
| 出口地址族 | 两个独立出口 IP 查询分别返回 IPv4 和 IPv6，证实本轮隧道具备双栈出口 |
| iPhone 手机端后续验收 | 用户确认成功，具体成功率与网络类型未记录 |

同一台服务器和同一套 Hysteria2 服务，入口从 IPv4 改为 IPv6 后完成了上述验收。但早先失败的 IPv4 测试和通过的 IPv6 测试相隔约 1.5 小时，只能作为跨时段比较；结合前一节 10 月 17 日同分钟 TCP 22 对照，两条入口路径的实际性能差异得到进一步支持。仍然无法据此断言人为封锁或定位丢包网元。

## 五、证据边界与快速复现

- 18:48 的 10/10 是 UDP 发包后收到 ICMP 端口不可达；19:23、19:26、19:29 是真实 39001/udp Echo；19:28 则是在 39000/udp 给 Hysteria2 发送无效 QUIC 报文的零响应。四种观察不能混用来计算应用层成功率。
- TCP 22 的 1/10 和 1/3 均为真实记录，但分别属于同分钟配对测试和随后的小样本探测。
- 最终验收验证了 Mac 的 IPv6 路径；手机端成功来自用户后续自测确认，详细成功率和网络类型并未记录。
- 可参考 [macOS 物理网卡对照脚本](../scripts/mac_path_probe.py) 对故障 IP 和对照 IP 进行低频轮换 TCP / TLS 握手检测。
