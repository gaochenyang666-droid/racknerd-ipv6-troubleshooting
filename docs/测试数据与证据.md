# 测试数据与证据

> 数据整理自 2026 年 10 月 15 日至 17 日的个人测试记录。不同时间、样本量及测量方式的数据不能直接混用为同一成功率。

## 一、服务器侧与外部对照

| 测试 | 记录结果 | 支持的结论 | 不能证明 |
| --- | --- | --- | --- |
| 服务器 loopback 代理测试 | 全部通过 | 软件具备本机运行能力 | 外部路径稳定 |
| 六个海外探测点访问服务器端口 | 很快成功 | 端口对部分其他来源可达 | 本地运营商路径可达 |
| 关掉客户端 VPN 后测试 | 失败仍持续 | 故障不完全依赖 VPN 运行状态 | 所有本地网络设置均无影响 |
| SYN 与 SYN-ACK 双端抓包 | SYN 到服务器，服务器发送 SYN-ACK，Mac 收到约一半 | TCP 返回路径有显著异常 | 具体丢包设备、过滤原因 |
| 同一分钟其他海外站点访问 | 接近 100% | 本地国际流量并未全部失败 | 所有其他 IP 必然稳定 |

### 为什么不能把“UDP 10/10”当成隧道可用？

向关闭的 UDP 端口发送报文时，服务器可用 **ICMP Destination Unreachable / Port Unreachable** 回答。客户端套接字可能因此报告 `Connection refused`。这能支持报文的去程和 ICMP 回程可达，但没有验证服务端应用返回真实 UDP 载荷，更没有验证 QUIC 的多轮握手与持续吞吐。

## 三、IPv6 最终验收

| 项目 | 测得结果 |
| --- | ---: |
| IPv6 TCP 建连 | 20/20 |
| IPv6 SSH 握手 | 10/10 |
| 通过 Hysteria 2 代理的真实 HTTPS 请求 | 20/20 |
| 真实 HTTPS 平均耗时 | 约 0.97 秒 |
| Google `generate_204` | 返回 HTTP 204 |
| YouTube、Telegram | 可达 |
| 代理出口 IP | 核对正确 |
| 下载 | 约 5.8 Mbps |
| 上传 | 约 11 Mbps |
| 连续 10 分钟测试 | 68 次请求，零失败 |
| iPhone 手机端后续验收 | 用户确认成功，具体成功率与网络类型未记录 |

此轮对照的核心变量是**服务器入口从 IPv4 改为 IPv6**。这有力说明原来失败的瓶颈与 IPv4 路径相关，但不能断言发生了人为封锁，也不能直接定位丢包网元。

## 四、未验证事项

- iPhone 已由用户确认连接验收成功；Wi-Fi / 蜂窝数据分项样本、具体 HTTPS 成功率和分流测试记录尚未提供。
- 上传、下载的长周期波动及峰谷时段差异。
- Mac 关机状态下的证书自动续期。
- 不同客户端网络对 RackNerd IPv6 的稳定性。
